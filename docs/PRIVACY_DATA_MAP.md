# 개인정보 데이터 맵

> 상태: 초기 설계 + 2026-07-14 3차 감사 Slice 1~3 구현 반영. 출시 전 공급자, 법적 근거, 잔여 보존 기간과 삭제 SLA를 확정해야 합니다.

## 확정 원칙

- 음성·사진을 외부 AI 공급자에게 보내기 전에 처리 목적과 공급자 공유를 명시하고 동의받습니다. (구현됨, Slice 1 강화: `ai_processing_consents`가 서버 관리 disclosure revision에 bind되고, **모든** provider usage kind의 예약이 current-revision 동의를 요구합니다. 동의가 없으면 업로드는 Supabase 저장까지만 가고 서버는 구조 검사만 수행합니다 — 외부 AI 호출 0회.)

- AI는 친구 발언을 더 강한 사실로 변형하지 않습니다. 범죄 이력, 건강, 성생활, 재산, 직업, 학력 등 민감·객관 주장에는 Dater 확인을 요구합니다.
- AI 결과는 사람이 편집하고 Dater가 공개 전 최종 승인합니다.
- 원본 음성은 승인·렌더 완료 후 짧게 보존하고 사용자가 즉시 삭제할 수 있게 합니다. 비용 모델의 초기 lifecycle 기준은 승인 후 7일입니다.
- public pitch asset과 원본 media bucket을 분리하고 signed URL과 최소 권한을 적용합니다.
- 정확한 위치, 전화번호, 이메일, 법적 이름과 신원확인 원본은 public payload에 포함하지 않습니다.
- 정부 신분증은 자체 저장하지 않고 가능한 경우 검증 공급자가 처리합니다.
- analytics에는 민감한 음성·사진·메시지 내용을 보내지 않습니다.
- 삭제·동의 철회·신고·차단 기능은 결제 여부와 무관합니다.

### 2026-07-14 확정분 (3차 감사 Slice 3·5, DECISIONS 참조)

- **Introducer 계정 삭제**: 본인이 녹음한 voice는 개인 데이터로 삭제 시점에 즉시 제거하고, voice를 잃은 published/paused 캠페인은 archived로 전이합니다(무성 피치를 계속 공개하지 않음). Dater 소유 데이터는 보존. 물리 storage object 제거는 service-role 삭제 잡이 수행합니다.
- **RevenueCat review payload**: resolved 후 90일 경과 시 PII를 scrub하고 요약만 유지합니다(`scrub_resolved_purchase_review_payloads`, 정기 ops 대상). open review는 운영 필요로 보존.
- **로컬 기기 위생(모바일)**: raw consent token은 승인/거절/만료 확인·publish·계정 전환 시 purge되고, 업로드 완료 draft의 로컬 미디어 사본은 publish 후 파일까지 삭제를 시도합니다.
- **profile-media**: 사용자 본인 prefix에 한해 클라이언트 삭제가 허용되어 Remove/rollback이 storage object를 실제로 제거합니다(orphan cleanup은 잔여 안전망).
- **이벤트 알림 이메일(0058, 2026-08-11)**: 이메일 주소는 계속 `auth.users`에만 존재합니다. `notification_outbox`가 저장하는 것은 **수신자 user id(`recipient_user_id`) · 닫힌 집합의 event type · 출처 행 외래키 두 개 중 정확히 하나(`interest_id` 또는 `render_job_id` — 이것이 곧 멱등 키입니다) · 착지 파라미터(`pitch_draft_id`, 렌더 완료 이벤트만) · 상태·시도 횟수·lease·타임스탬프**가 전부입니다. 주소도 자유 텍스트도 담지 않습니다 — 유일한 텍스트 컬럼 `last_error`는 **allowlist CHECK(`^[a-z0-9_]{1,60}$`)** 로 사유 코드 형태만 허용하므로 주소·전화번호·URL·공급자 문장이 모두 거부되고, 발송기도 같은 형태로 정규화합니다. 주소는 발송 순간 service-role로 해석되어 Resend에 전달되고 즉시 폐기되며, 로그·응답 요약·ops alert 어디에도 남지 않습니다. 메일 본문에 들어가는 개인정보는 **수신자 본인의 display name 하나**이고, 상대 이름·프로필·사진·관심 노트·메시지 본문·campaign slug는 포함하지 않습니다. 4종 전부 거래성 통지라 마케팅 옵트아웃은 두지 않았고, 정지·삭제 계정에는 적재도 발송도 되지 않습니다. 72시간이 지난 미발송 항목은 발송되지 않고 종결됩니다. 공급자는 Resend(발송 메타데이터 보존 기간은 공급자 정책 — 확정 필요).
- **display name(0061, 2026-09-08, T002)**: `private.handle_new_auth_user`(0011)는 가입 시 `profiles.display_name`을 **이메일 local-part**로 채우고 `display_name_confirmed=false`로 표시합니다. 이메일 주소의 앞부분은 그 자체가 개인정보이므로, **확인되지 않은 display name은 공개 표면에 나가지 않습니다**. 게이트는 두 곳입니다 — ① 익명 호출자가 직접 부르는 유일한 공개 리더 `get_consent_preview`는 **DB에서** `introducer_display_name`에 NULL을 돌려주고(0061), ② 나머지 공개 표면(공개 캠페인 페이지 `/p/<slug>`, OG 카드 `/api/og`, 런치 킷 이미지 `/api/kit-image`, 이벤트 알림 메일 인사말)은 `packages/data`의 `publicDisplayName` 한 함수를 통과하며 이름 대신 `'A friend'` 또는 이름 없는 인사말("Hi,")을 인쇄합니다. **범위 밖**: 관심 목록·intro room·소개한 캠페인 목록 등 **이미 서로를 아는 두 사람 사이의 화면**은 게이트하지 않습니다(공개·무가입 열람 경계 밖이고, 이름을 지우면 대화 상대를 식별할 수 없게 됩니다). 소개자는 모바일에서 피치를 보내기 직전에 이름을 직접 고르며(입력 필드는 local-part로 **미리 채우지 않습니다**), 계정 화면에서 언제든 바꿀 수 있습니다. **확정 필요**: `generate_campaign_slug`는 dater의 display name으로 공개 URL 슬러그를 만듭니다 — 현재는 웹 동의 플로우가 승인 전에 이름을 확인시켜 미확인 이름이 슬러그가 되지 않지만, 이 순서를 강제하는 것은 UI이지 DB가 아닙니다.
- **이벤트 알림 큐와 삭제 경로(정확히)**: 계정 삭제(`request_account_deletion`)는 `users` 행을 **지우지 않고** `account_status = 'deleted'`로 전이시킵니다(0037). 따라서 `recipient_user_id`의 `ON DELETE CASCADE`는 이 경로에서 **발동하지 않으며**, "계정 삭제 시 CASCADE"라고 적으면 사실과 다릅니다. 실제로 보장되는 것은 세 가지입니다 — ① `enqueue_notification`이 `account_status = 'active'`가 아닌 수신자에게는 **행을 만들지 않고**, ② `claim_notification_outbox`가 적재 후 상태가 바뀐 수신자를 **절대 claim하지 않으며**(정지·삭제 사이 창을 막습니다), ③ 남은 미발송 행은 72시간 뒤 종결됩니다. 실제 CASCADE는 **출처 행이 삭제될 때**만 일어납니다: `interests`·`media_render_jobs`·`pitch_drafts` 삭제 시 관련 outbox 행이 함께 사라지고, `users` 행 자체를 물리 삭제하면 그때 수신자 기준으로도 사라집니다. 렌더 잡의 `requested_by_user_id`는 계정 소거 시 `SET NULL`이므로(0054) 소거 후 완료되는 렌더는 "알릴 사람 없음"으로 적재 자체가 생략됩니다. 종결된 행은 식별자와 사유 코드만 남으므로 개인정보 삭제 대상이 아니지만, 보존·정리 주기는 **확정 필요**입니다.

- **Dater 쪽 잔여 정리는 기존 takedown이 답입니다(2026-08-12 확인, 신규 경로 없음)**: 공개된 캠페인을 내리는 것은 `/inbox`의 "Take it down for good"(`set_campaign_status` → `archived`)이고, 그 이상의 "캠페인째 삭제"는 **의도적으로 만들지 않았습니다**. archived 캠페인 행에는 그 캠페인에 관심을 보낸 **다른 사람들의** `interests`와 양쪽 메시지가 달린 `intro_rooms`가 매달려 있고, 그 draft에는 Dater 본인이 승인한 `consent_revisions` 스냅샷이 들어 있습니다. 캠페인을 지우는 버튼은 타인의 데이터와 자신의 승인 기록을 함께 지우는 버튼이 됩니다. archived는 이미 공개를 멈추고(공개 읽기 차단) 새 관심 유입도 멈추므로 "정리"의 관찰 가능한 목적은 달성됩니다. 계정 전체를 지우고 싶은 사람에게는 계정 삭제가 그 경로이며, 그쪽은 위 표대로 캠페인·관심·룸을 실제로 지웁니다.

- **waitlist 이메일(Slice 5, 2026-08-12 Issue #52로 발송·삭제 정책 확정)**: `waitlist_signups`는 출시 초대 연락 목적의 이메일과 유입 캠페인 연결만 저장합니다. service-role 전용 읽기(클라이언트 조회 불가), 시간당 가입 cap, 중복 no-op. 로그·analytics에 이메일을 남기지 않습니다. **발송·삭제(확정)**: 이 주소는 **정확히 한 통**의 메일에만 쓰입니다 — iOS 앱이 스토어에 오른 날의 초대. 그 메일은 수신자별 개인화가 전혀 없고(이름·source·referral·추적 파라미터 없음) 본문이 삭제 사실을 말합니다. **발송에 성공하는 순간 그 행이 삭제**되므로 목적이 끝난 주소는 보관되지 않고, 그래서 수신 거부 링크도 두지 않았습니다 — 구독할 대상이 남지 않습니다. 실패한 발송은 행을 남겨 다음 실행이 재시도합니다. 처리 상태 컬럼은 만들지 않았습니다: **"행이 남아 있음"이 곧 "아직 안 보냄"**입니다. 삭제 요청은 `node scripts/send-waitlist-invites.mjs --forget`(stdin 입력, 정확 일치만)이 처리하고 실행 영수증에는 행 id와 결과만 남습니다. 랜딩 문구가 이 계약을 그대로 말합니다("One email, the day the app is out — then your address is deleted"). 공급자는 Resend. **실발송 자체는 사용자 결정 항목입니다.** 절차는 `docs/OPS.md` → waitlist 초대와 삭제.
